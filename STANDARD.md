# The PublicDataToolkit standard

**Version 0.1, draft, 2026-11-19.** Written for the snake_case spike (Task 5 on the [project board](PROJECT_BOARD.md)) and expected to change once the GSS, ANES and MTF slices test it. The parts most likely to change are listed in §10.

This file says what a finished dataset repository must contain. An agent building or improving a dataset repo reads this file, follows [`instructions/`](instructions/README.md), and finishes when `pdt check` passes (§9). The JSON Schemas in [`schema/`](schema/) are the exact form of the records described here. Where this file and a schema disagree, fix whichever one is wrong; don't work around it.

The reasoning behind the standard is in [`planning/plan.md`](planning/plan.md) §3–4 and in §2 and §5 of the [earlier plan](planning/survey_metadata_packages_plan.md).

## 1. What a dataset repository is

One repository describes one dataset across all its releases: for example the GSS cumulative file, the ANES Time Series Cumulative Data File, or the Monitoring the Future 12th-grade survey. It holds:

- metadata records for every variable in every release it covers, built from the publisher's documentation;
- the code that builds those records, so anyone can rebuild them from a clean clone;
- a way to get the data: a GitHub release when the terms allow it, otherwise a download script;
- three generated forms of the metadata: a site for people, a Python API and JSONL for code, and shards for LLMs.

It does **not** hold analysis decisions: which answers count as agreement, weights, harmonized recodes, or which variables a project uses. Those stay in the projects that use the repo. The repo does ship an **extract builder** (`scripts/extract.py`): the user names the variables, years and how to treat each missing type, and it writes the extract. Its options encode no analysis choices of their own.

**Name.** A dataset repo is named `pdt-<dataset-id>`, where `<dataset-id>` is the `id` in `dataset.yaml`: lowercase letters, digits and hyphens, starting with the name people already use for the dataset. Examples: `pdt-gss`, `pdt-anes-cdf`, `pdt-mtf-12`, `pdt-chicago-crimes`. The name has no language, release, version or publisher in it: the repo is language-neutral, covers every release, and outlives versions of the standard. Add a qualifier only to tell apart two products of one study (`anes-cdf`, `anes-panel`) or two places. Python code in the repo uses underscores (`pdt_gss`). Before building, claim the id in this toolkit's registry (not yet created), and give the repo the GitHub topic `publicdatatoolkit`. The reasoning is in [`planning/versions_layout_names.md`](planning/versions_layout_names.md).

## 2. Layout

```text
pdt-<dataset-id>/
  README.md                  required sections in §2.3
  CLAUDE.md                  instructions for agents working in the repo
  EXTENSIONS.md              every extension key used, with a reason (§4.4)
  dataset.yaml               the dataset, its terms and releases      schema/dataset.schema.json
  sources.yaml               every file the repo depends on           schema/sources.schema.json
  .copier-answers.yml        which template version the repo was made from (§2.4)
  Makefile                   download, build, views, check (§2.4)
  pyproject.toml             depends on the shared library
  .env                       gitignored; logins for sources that need them
  scripts/download.py        fetches sources; --check; refuses to run until terms are accepted
  scripts/extract.py         builds an extract the user specifies (§8)
  build/                     parsers: publisher documentation -> records
    report.md                generated by the build: what it checked against the data (C3-C5, C12) until pdt check runs those checks
  metadata/
    releases/<release>/variables.jsonl   one variable per line        schema/variable.schema.json
    releases/<release>/<table>/variables.jsonl   instead, when the release has several tables (§2.1)
    groups.jsonl                         batteries, sections, ...     schema/group.schema.json
    links.jsonl                          continuity across releases   schema/link.schema.json
    histories.jsonl                      code histories (optional)    schema/history.schema.json
    code_lists.jsonl                     shared code lists (optional) schema/code_list.schema.json
    corrections.jsonl                    errata                       schema/correction.schema.json
    derived/<property>.jsonl             generated by rule            schema/derived.schema.json
    annotations/<name>.jsonl             topics, aliases, summaries   schema/annotation.schema.json
  references/                publisher documentation that the terms let us commit
  docs/                      generated site (§7); served by GitHub Pages
  agent/                     generated (§7)
  export/data-dict/<release>.yaml        generated (§7)
  tests/
  data/                      gitignored
    raw/                     download.py writes here; never edited
    interim/                 parser intermediates, e.g. pdftotext output
    processed/               files for the data release, when terms allow
```

The names `data/raw`, `data/interim`, `data/processed`, `references/` and `docs/` mean what they mean in [Cookiecutter Data Science](https://cookiecutter-data-science.drivendata.org/), so the layout is familiar to its users. The rest of the CCDS layout (`models/`, `reports/`, `notebooks/`, `features.py`) is for analysis projects and isn't used.

| Kind of file | Who writes it | Edited by hand? |
|---|---|---|
| `dataset.yaml`, `sources.yaml`, `corrections.jsonl`, `EXTENSIONS.md`, README, CLAUDE.md | a person or an agent | yes |
| `variables.jsonl`, `groups.jsonl`, `links.jsonl` | `build/` | no: change the parser, or add a correction |
| `derived/` | the shared library's rules | no |
| `annotations/` | people, rules or models | yes, with origin recorded |
| `docs/`, `agent/`, `export/` | the shared library | no |

**Large views.** `agent/` and `export/` are committed, because agents and data-dict read them from a clone. `docs/` may be left out of git (listed in `.gitignore`) and built and published to GitHub Pages instead; a repo should do that once `docs/` passes about 25 MB, as the full GSS's 123 MB does. C8 then checks `docs/` only where it exists.

Hand edits to source records are not allowed because the next build would silently undo them. A fact the parser can't produce goes in through a hand-written input to `build/` (a small YAML of additions, for instance), recorded with `origin: hand`.

### 2.1 `dataset.yaml`

Names the dataset and its publisher, records the terms (§8), and lists the releases the repo covers. Each release has an `id`, which is also its directory under `metadata/releases/`, and the list of source files its records were built from.

A release whose data describe an earlier period than the collection, such as ASEC 2024's income in 2023, gives it in `reference_period`.

**Release ids** use the publisher's own name for the release, written lowercase, with no spaces: `7224r3a` for the GSS (from NORC's file name), `20260205` for the ANES (its version date), `2022-2023` for the NSFG (its cycle), `2024` for FARS (its data year). When the publisher has no name for a release, use its date, `YYYYMMDD`.

**Revisions within a release.** A publisher can reissue a release's files without making a new release: NHTSA reissued the 2017 FARS files until 2022, and revised the 2017 data itself in December 2020. A release may list these in `revisions`, each with its date, what changed, and its source (such as a release note). The checksums in `sources.yaml` identify which revision a build used. A revision isn't a link: `data_revised` (§5.2) is for changes between releases.

**Tables.** Some releases have several files: the NSFG has female respondents, male respondents and pregnancies, and FARS has crashes, vehicles and persons. A release like that lists its `tables`. Each table has:
- an `id`, which is also its directory under the release;
- a label, and the source files it comes from;
- the `key` columns that identify a row;
- `references` to other tables, like foreign keys: a pregnancy's `CASEID` refers to the female respondent table. A reference that holds only for some rows names them with `when`: a FARS person's (`ST_CASE`, `VEH_NO`) refers to the vehicle table only `when` `PER_TYP` is an occupant of a vehicle in transport. Columns can have several references, with different conditions and targets.

Its records go in `metadata/releases/<release>/<table>/variables.jsonl`. A release with one file lists no tables and keeps its records in `metadata/releases/<release>/variables.jsonl`. A reference can also point to a table in another dataset, such as a code list published separately.

`domain` names its broad subject area in one word (`health`, `social`, `labor`, `education`, `election`, `crime`), for exports and catalogs that group datasets. It's optional.

`kind` says what sort of dataset it is: `survey`, `administrative` (FARS) or `portal` (a table on an open-data portal). It's optional, and tunes what C6 reports.

**Partial data files.** When a release's or table's common-format file holds only some waves, because the table is too large or keeps growing, `data_waves` lists them, and C5 checks availability only for those. When it holds only some rows of each wave, such as some countries, `data_rows` names the `column` and the codes it keeps (`in`), and C3–C5 read it the same way.

`design` names the survey design variables: `weights`, `strata` and `psu`, and `replicates` when variance comes from replicate weights. `replicates` names the weights, as a list of `variables` or a `prefix` and a count `n`, and the `table` that holds them when it's another table (with the `key` it joins on), and the `method` (`brr`, `fay`, `jk1`, `jkn`, `bootstrap`, `sdr`, `other`), with `fay_factor` for Fay's method: PISA's 80 weights `W_FSTURWT1`–`W_FSTURWT80` use Fay's method. When the design variables are in another table than the one described, as the NLSY's strata and PSU are in its person table, `design.table` and `design.key` say where. A weight used only in some waves is an object with its `name` and `waves` (ATUS: `{name: TU20FWGT, waves: [2020]}`); the others apply to every wave. A release or table can override it. A variable named in `replicates` needs no record of its own: C3 accepts it. It's descriptive: which weight suits an analysis is the user's choice.

`dimensions` says what availability's `wave`, `form`, `sample`, `mode`, `phase` and `geography` mean for this dataset. `geography` is where a question was asked when that varies, such as a BRFSS state module (`{"wave": 2022, "geography": "25"}`, Massachusetts); `dimensions.geography.label` names the unit. For the GSS, a wave is a year and a form is a ballot; for MTF, a form is a questionnaire form. The library treats them all the same way; the labels are for people and for rendered pages.

### 2.2 `sources.yaml`

Every file the repo depends on: data files, codebooks, questionnaires, release notes, errata pages, crosswalks and upstream packages. Each entry records the URL or how to get the file by hand, where `download.py` puts it, which releases it belongs to, whether it may be redistributed, and, once fetched, the date, size and SHA-256.

A source that can't be downloaded automatically (a login, a click-through, a site that blocks scripts) is fine as long as `manual_steps` says exactly what to do. An undocumented file is not fine.

A **live** source (`live: true`), such as an open-data portal's table or metadata API, changes in place. Its `sha256` identifies the snapshot the build used, and a later mismatch reports the source as changed since the snapshot, not as a failed download. The release id is the snapshot's date.

An upstream package (gssrdoc, for instance) records the release tag or commit it was pinned to in `version`. A source that documents a release, such as a codebook or an upstream package, lists the releases it documents in `documents`, which can differ from the release it's used for: gssrdoc 0.9 documents `7224r3` and is used for `7224r3a`. A mismatch between `documents` and a source's use is then data, which `pdt check` can report, rather than a note. A codebook that lists a code only when the data has cases with it, as the NSFG's does, says so with `lists_only_occurring_codes`, so a comparison of releases doesn't read a code's absence as a change.

### 2.3 README and CLAUDE.md

The README has these sections, in this order: what the dataset is; terms of use, including `terms.notice` verbatim when the terms require a credit or disclaimer; how to get the data; how to use the metadata (all three forms); how to cite the dataset and this repo; how to rebuild.

CLAUDE.md tells an agent working in the repo where things are, which files are generated, and to read `agent/index.md` before searching the metadata.

### 2.4 Versions and updates

The standard, the template and the shared library share one version number, set by tagging a release of this toolkit. `standard_version` in `dataset.yaml` says which version a repo meets, and `pdt check` validates against that version's schemas, so a repo that isn't upgraded keeps passing.

| Change | Version bump | What a dataset repo has to do |
|---|---|---|
| Breaking: a field renamed or restructured, a new required file | major | upgrade (below) |
| Additive: a new optional field, a check that only warns | minor | nothing; update when convenient |
| Fix | patch | nothing |

Dataset repos are generated from `templates/` with [Copier](https://copier.readthedocs.io/), which records the template version in `.copier-answers.yml`. To upgrade:

1. `copier update` brings the template's files forward (Makefile, CI, tests, skeletons) and runs any migrations, such as renaming a field in every JSONL line.
2. The new shared library regenerates `docs/`, `agent/` and `export/`.
3. For dataset-specific code (`build/`, hand-made inputs), an agent follows the upgrade guide for that major version, `instructions/upgrade/v<N>-to-v<N+1>.md`.
4. The repo is upgraded when `pdt check` passes at the new version.

Before 1.0 there are no compatibility promises and no migrations.

Every repo has the same Makefile targets, so the same commands work everywhere: `make download`, `make build` (sources to records), `make views` (records to `docs/`, `agent/` and `export/`), and `make check`.

## 3. Rules for every record

1. **Describe the data; don't analyze it.** Question wording, codes and missing codes belong in the records. "Count agree and strongly agree as 1" does not.
2. **Keep the publisher's identity.** Names are stored exactly as published, case included. A link between two variables records continuity the publisher asserts (the same GSS name across releases, an MTF crosswalk, a cumulative-file variable built from single-year items), never equivalence we infer.
3. **Copy text verbatim.** Question text, labels and notes are copied exactly, typos included. A parser may remove layout artifacts: line breaks introduced by page width, hyphenation at line ends, running headers. It may also fix an artifact that affects a source throughout, such as gssrdoc's doubled apostrophes, by a named, versioned rule recorded in the field's provenance. Anything that affects one variable is a correction (§5.3), not an edit.
4. **Leave a field empty rather than guess.** Not every source provides every field, and not every dataset fills every field.
5. **Store structure as structure.** Lists are lists and objects are objects. Strings like `"[1] yes / [2] no"` or `"1972, 1973, ..."` appear only in generated views.
6. **Keep source, correction and derivation apart.** Source records hold what the publisher says. Corrections live in `corrections.jsonl`. Derived properties and annotations live in their own files. The library combines them when it builds the views, and the views label which is which.
7. **Every fact has an origin.** See the table below.
8. **Model drafts are allowed, labeled, and checked.** An agent may draft records with an LLM, for example from a PDF codebook. Those records carry `origin: model` with the model, the date and `reviewed`. They are validated like any other record, and `pdt check` reports how many are unreviewed. Links may not come from a model.

### Origins

Each variable record has `provenance.record`, the origin of the record as a whole, and `provenance.fields` for fields that came from somewhere else. Each missing code has its own `origin` (§4.2). Groups, links and annotations each have one `origin`.

| `origin` | Meaning | Required with it |
|---|---|---|
| `publisher` | read from the publisher's documentation | `source` (an id in `sources.yaml`); `location` when practical |
| `upstream_package` | read from a third-party package that redistributes the publisher's documentation (gssrdoc) | `source` |
| `data_file` | read from the data file's own metadata: Stata or SPSS labels, extended missing values | `source` |
| `rule` | computed by a named rule from other fields | `rule`; `rule_version` |
| `hand` | a judgment entered through a hand-written build input, by a person or an agent. `author` names who made it: a person, or the agent and its task ("Claude (PublicDataToolkit Task 35)"), never a person who didn't make or check it | `author`, `date` |
| `model` | drafted by an LLM | `model`, `date`, `reviewed`; `prompt_version` when there is one |

## 4. Variable records

One line per variable in `metadata/releases/<release>/variables.jsonl`, or `.../<release>/<table>/variables.jsonl` for a release with tables. The same name in two releases is two records; links (§5.2) say how they relate. The same name in two tables of one release (`MARSTAT` for women and for men) is also two records, and every reference to it must name its `table`; `pdt check` fails an ambiguous reference.

### 4.1 Fields

| Field | What it holds |
|---|---|
| `dataset`, `release`, `name` | Required. Together with `table`, when the release has tables, they identify the record |
| `label` | The publisher's short label |
| `description` | The publisher's definition or description, verbatim. For data without questions, such as FARS, this is the main text |
| `questions` | Question text. Usually one entry. When the wording differs by wave, form or mode, one entry per wording, each saying where it applies (`waves`, `forms`, `modes`). A wording used only under a condition ("if R is married") says so in `condition`, in the publisher's words. When the publisher separates a battery's shared stem, the item text and interviewer instructions, keep them in `stem`, `item` and `instructions` as well as the full `text`. The questionnaire's item number (AD-7b, Q26) goes in the wording's `number`, or, when the same wording is numbered differently by wave, in `numbers`, each with its waves. A wording from a different document than the record's other facts carries its own `origin` |
| `variable_type` | How the variable was produced, when the publisher says: `response` (a direct answer or observation), `recode`, `computed`, `imputation_flag`, `weight`, `design`, `administrative` (paradata, records added by the publisher), `other`. A flag variable (allocation, imputation, top-code, swapping) names what it flags in `flag_for`. A variable that stands for one code in a list, such as ATUS's `t010101` (minutes on lexicon code 010101, "Sleeping"), names it in `code_of` (`{code_list, code}`). When the publisher's file holds the variable in a different column in each wave, as the NLSY's wide file does (YHEA-100 is R0320600 in 1997, another reference number each round), `source_columns` lists them (`[{waves, column}]`), and the common-format table is long, one row per person and wave |
| `storage_type` | How the value is stored: integer, float, string, date, datetime, boolean, geometry |
| `measure` | What kind of quantity the valid values are: categorical, ordinal, continuous, count, identifier, weight, text, date |
| `values` | Every documented code, valid and missing, in the publisher's order (§4.2). A code's `n` is its count of cases, when the codebook prints one; when the codebook prints counts by wave, they go in `counts` (`[{wave, n}]`) and `n` is their sum. A code's `note` is the publisher's note on that code, verbatim, such as how a calculated variable's code is derived |
| `code_list` | The id of a shared code list (§4.5) whose codes come before `values`' own |
| `valid_range` | For numeric variables whose valid values aren't all labeled, such as thermometers and ages: min, max, and whether the ends are top- or bottom-coded. Labeled points inside the range (A_AGE's 80 "80-84 years of age") are listed in `values` as valid codes too. When the valid values form several ranges with different meanings, `valid_range` is a list, each range with its `label`: BRFSS ALCDAY5's 101–107 (days per week) and 201–230 (days in the past 30) |
| `implied_decimals` | When numbers are stored without their decimal point (a weight of 255212 meaning 2552.12): the number of implied places. The data keep the stored value |
| `units`, `universe`, `notes` | Verbatim from the publisher. When the universe differs by wave, as in a panel's rounds, `universe` is a list of `{text, waves}` |
| `availability` | One entry per (wave, form, sample, mode, phase) combination the publisher documents. An entry with only `wave` means everyone in that wave. `n` is the count of non-missing responses, when known |
| `source_location` | Where a person can read this variable's documentation: source, page, URL, anchor, and the publisher's own id for it |
| `provenance` | Required. §3 |
| `extensions` | Dataset-specific fields (§4.4) |

Required fields are few on purpose (rule 4). `pdt check` reports how many records lack a label, question text or values, so gaps are visible.

### 4.2 Values and missing codes

Each code has `code`, `label`, and `kind`, which is `valid`, `missing` or `unresolved`. A missing code also has `missing_types`. Missing and unresolved codes need an `origin`: their own, or the record's default, `provenance.codes`, when many codes share one. For an unresolved code, the origin's `note` says what was checked.

**Labels for one release.** When a release's documentation covers many years, as FARS's 1975–2024 manual does, a label can carry history ("Unknown/Reported as Unknown (Since 2018)"). The record uses the label specific to its release when a source gives one, such as the data file's own label ("Reported as Unknown"), with that source as the values' origin.

Codes are stored as they appear in the data file: numbers as numbers, and Stata extended missing values as strings such as `".d"`. When the documentation gives other codes for the same values, as PISA's 2022 codebook gives 9999995–9999999 (the SAS files' codes) where the SPSS file has 95–99, the record keeps the data file's codes, matches them to the documentation by label, and says so in the codes' origin `note`.

**Retired codes.** A code the publisher has retired but that still occurs in earlier data stays `valid`, with `retired: true` as the publisher marks it, and `waves` (`{from, to}`) when the publisher says when it was in use.

**Missing types.** One code can have several, as GSS `.m` "dk, na, iap" does.

| Type | Meaning | Examples |
|---|---|---|
| `dk` | The respondent didn't know or couldn't choose | GSS `.d`; ANES 98 "DK" |
| `refused` | The respondent refused | GSS `.r` |
| `no_answer` | No answer recorded, reason unknown | GSS `.n`; ANES 99 "NA" |
| `inap` | Not applicable: outside the universe or skipped by design | GSS `.i` "iap" |
| `skipped` | The respondent skipped it (self-administered modes) | GSS `.s` "skipped on web" |
| `not_asked` | Not asked of this respondent's wave, form or interview, including a panel round the respondent missed | GSS `.y` "not available in this year"; ANES "no Post IW"; NLSY -5 "non-interview" |
| `not_available` | Asked, but not released in this file | GSS `.x` "not available in this release" |
| `uncodeable` | Answered, but couldn't be coded or imputed | GSS `.u`, `.p` |
| `unknown` | The source records the value as unknown. For administrative and coded data, where no respondent was asked | FARS "Unknown", "Reported as Unknown" |
| `unspecified` | The source marks the code missing but gives no reason | GSS `.z` "see codebook" |
| `other` | Anything else; say what in the label | |

**Which codes are missing, in order of preference:**

1. The publisher marks them, as the ANES codebook's "Missing" section and NORC's "RESERVED CODES" do. `origin: publisher`.
2. The data file marks them, as Stata extended missing values do. `origin: data_file`.
3. A rule over labels, used only when neither of the above exists. `origin: rule`, with the rule's name.
4. A person or an agent adds one the others missed, such as an out-of-universe code. `origin: hand`, with the author named.

**When the sources don't say,** the code is `unresolved`: a code in the data with no label, or a label like "see codebook" that the codebook doesn't explain. Don't guess a type to get past the check. A wrong classification is worse than an open one, because recoding code would silently trust it. `pdt check` reports unresolved codes and doesn't fail on them. Unresolved isn't a kind of missing: the library never recodes an unresolved code by missing type, warns when a variable it recodes has any, and handles them only when the caller asks explicitly.

A code's `kind` follows the publisher of that release even when its label suggests otherwise. If a later release classifies the same code differently, each release's records say what that release's publisher said, and each release's data is read with its own records. The ANES codebook lists VCF0803 code 9, "DK; haven't thought much about it," under **Valid**, so it is stored as valid; a follow-up item depends on it. If a publisher's marking looks like an error, record a correction (§5.3).

The point of typing missing codes is that the library can recode them by type, for example DK to one value and INAP to another, instead of collapsing them all into one NaN, which is what the existing GSS and ANES code does ([inventory](planning/inventory.md) §3).

### 4.3 Example

A GSS record, shortened (the full one is in [`schema/examples/gss/variables.jsonl`](schema/examples/gss/variables.jsonl)):

```json
{
  "dataset": "gss", "release": "7224r3a", "name": "abany",
  "label": "abortion if woman wants for any reason",
  "questions": [{
    "text": "Please tell me whether or not ... \nG. The woman wants it for any reason?",
    "stem": "Please tell me whether or not you think it should be possible for a pregnant woman to obtain a legal abortion if. . .",
    "item": "G. The woman wants it for any reason?",
    "instructions": "READ EACH STATEMENT, AND CIRCLE ONE CODE FOR EACH."
  }],
  "storage_type": "integer", "measure": "categorical",
  "values": [
    {"code": 1, "label": "yes", "kind": "valid"},
    {"code": 2, "label": "no", "kind": "valid"},
    {"code": ".d", "label": "don't know", "kind": "missing", "missing_types": ["dk"],
     "origin": {"origin": "upstream_package", "source": "gssrdoc"}},
    {"code": ".m", "label": "dk, na, iap", "kind": "missing",
     "missing_types": ["dk", "no_answer", "inap"],
     "origin": {"origin": "upstream_package", "source": "gssrdoc"}}
  ],
  "availability": [{"wave": 1972}, {"wave": 1988, "form": "A"}, {"wave": 1988, "form": "C"}],
  "source_location": {"source": "gssrdoc", "upstream_id": 607,
                      "url": "https://gssdataexplorer.norc.org/variables/607/vshow"},
  "provenance": {
    "record": {"origin": "upstream_package", "source": "gssrdoc"},
    "fields": {"questions": {"origin": "rule", "rule": "split_stem_item_instructions", "rule_version": "0.1"}}
  }
}
```

### 4.4 Extensions

A fact the standard doesn't model yet goes under `extensions`, namespaced by dataset id: `"extensions": {"gss": {"subjects": [...]}}`. Every key used is listed in the repo's `EXTENSIONS.md` with a reason. During the spike, these lists are the main result: an extension that shows up in two datasets is a candidate for the standard.

### 4.5 Shared code lists

When the publisher publishes a list of codes separately (Chicago's IUCR codes), or one list serves several variables (GSS occupation codes for the respondent, spouse, father and mother), the list is stored once in `metadata/code_lists.jsonl` and each record names it in `code_list`. A list has an `id`, which names its version (`census-occ-2010`), a `label`, an `origin`, and its `codes`, each a value as in §4.2 (`code`, `kind`, usually `label`). A code can also have `retired`, `waves`, and `attributes` for the list's other columns, which the list's `columns` describe. The record's own `values` hold its other codes, usually the missing ones, which differ from variable to variable. A code can't be in both.

The library expands a record's list when it loads a repo, so every check and view sees the full set of codes. Only identical lists are shared; a list that changes is a new list with a new id. A list published as a table of data can also be a table in the release (§2.1) for joins in the data; the code list is its metadata.

**Harmonized lists.** When the publisher builds one list from others, as BLS's multi-year ATUS lexicon pools the single-year lexicons, the list names them in `harmonizes`, and a code says which of their codes it includes, and when, in `includes` (`[{code_list, code, waves}]`), from the publisher's own statement (020681 "includes 020601 (all years), 020602 (2008 and later years)").

## 5. Groups, links and corrections

### 5.1 Groups

`groups.jsonl` holds sets of variables: batteries, codebook sections, modules, questionnaire forms, and the publisher's subject lists. `kind` is `battery`, `section`, `module`, `form`, `subject`, `plausible_values` (draws of one score, such as PISA's PV1READ–PV10READ, to be analyzed together and never one alone), `variants` (versions of one item within a release, such as a GSS question asked in two wordings to random halves of the sample, `-v` and `-nv`) or `other`. A group has an `id`, a `kind`, its `members` (in order when `ordered` is true), and an `origin`. A battery can have its shared `stem`. A group can name a `parent`, such as the section that contains a battery.

Groups the publisher defines have `origin: publisher` or `upstream_package`. Groups found by a rule, such as a battery inferred from a shared stem and value set, have `origin: rule`. Queries on publisher groups can be `complete`; queries on rule groups are `complete_by_rule` (§7).

**Subjects.** When the publisher, or an upstream package that copies it, assigns variables to subjects or topics, as GSS Data Explorer does ("Abortion", "Race"), each subject is a group of kind `subject`. A variable can be in several. "Every variable NORC lists under Abortion" is then `complete`: complete with respect to the publisher's own list, which may well miss items a reader would call abortion items. Topics assigned by a person, a rule or a model stay annotations (§6).

**A repo that covers part of a release** (a slice) lists, in each group, only the members it has records for. Results are always complete with respect to the records in scope, and every result states its scope (§7).

### 5.2 Links

`links.jsonl` records continuity the publisher asserts between two variables, each named by release and name. `relations` lists everything that holds between them, because one pair can be both renamed and reworded:

| Relation | Meaning |
|---|---|
| `same_item` | The same question, asked the same way |
| `renamed` | The name changed |
| `wording_changed` | The question text changed |
| `codes_changed` | The value set changed |
| `range_changed` | The valid range or a top code moved while every code kept its meaning (Pulse TBIRTH_YEAR's yearly top code; THHLD_NUMPER 1–10 → 1–40) |
| `labels_changed` | The variable label or value labels changed (e.g. a corrected label). When the codes changed too, the link also lists `codes_changed` |
| `universe_changed` | Who was asked changed |
| `data_revised` | The same item, but its values in the data were revised between releases: recoded missing codes, restored or corrected data, reassigned cases. Release notes are the usual source |
| `derived_from` | `from` is built from `to`, as a cumulative-file variable is built from single-year items |
| `split_from`, `merged_into` | One variable became several, or several became one |
| `rescaled` | The same construct, but the scale was re-estimated, so values aren't comparable across the pair without the publisher's trend or linking file. PISA's ESCS and BELONG are re-estimated each cycle |

A link that holds only for some of the `from` variable's waves, as a cumulative-file variable is `derived_from` one year's item only for that year's rows, lists them in `waves`. When a crosswalk maps several yearly items, unchanged, to the same cumulative variable, `same_item` links between those yearly items may be made by rule from it, citing it as the source.

A link the publisher states can carry `evidence`, as corrections do (§5.3): a citation, URL and verbatim quote.

Every link names a `source`: a crosswalk, release notes, or a documented naming convention (`origin: rule`, for "the GSS keeps a name when the item is unchanged"). Links never come from a model (rule 8).

### 5.3 Corrections

`corrections.jsonl` records errors in the publisher's or upstream package's documentation. Each correction gives:

- the target: variable name, or a shared code list's id (§4.5), a JSON Pointer to the field (`/questions/0/text`, `/codes/12/label`), and optionally the releases;
- the `original` value and the `corrected` one;
- the `problem` in one sentence;
- `evidence`: at least one citation, with a URL when there is one;
- `confidence`: `verified` when a source confirms the corrected value, `inferred` when it's our best reading (from parallel items, for instance);
- `upstream`: whether it has been reported, with a link;
- the author and date.

**Corrections the publisher prints** in its own documentation, such as the NSFG's margin box "Corrected universe for MFLASTP", aren't errata of ours. They're what the publisher says. The record holds the corrected value, with the publisher as its origin and the box as its location, and keeps the superseded text in `notes`.

**A correction can classify a code.** It can change an `unresolved` code to `missing` (with its types) or to `valid`, when the evidence is strong, even if the publisher hasn't confirmed it. An example is the ANES 2024 codes that the cumulative codebook doesn't list but that match the 2024 study's own coding. Such a correction is `inferred` until the publisher confirms it, cites its evidence, and records the report to the publisher in `upstream`. Tools that rely on it say so: the views mark the corrected code, and recoding by missing type reports which codes it classified from an `inferred` correction. A code with too little evidence, like a single unexplained case, stays `unresolved`.

Source records keep the original of *our* corrections. The library applies corrections when it builds the views, and every view shows that a value was corrected. If the original no longer appears in the record, `pdt check` fails (§9, C7): usually upstream has fixed it, and the correction should be retired.

### 5.4 Code histories

Some publishers document every year of a long-running dataset in one place, as FARS's 1975–2024 manual does with a matrix of codes by year range for each element. That matrix records two kinds of change. The same code can change meaning (FARS `LGT_COND` 9 is "Unknown" until 2017 and "Reported as Unknown" from 2018), and the same answer can change code (`WEATHER`'s "Unknown" goes from 9 to 99).

A release's record says only what that release means (§4.2), and links (§5.2) connect variables, not codes. So the publisher's history is kept as data in `metadata/histories.jsonl`, written by the build with the publisher as its origin, one line per variable. A history assembled by rule from one-release documents, as BRFSS's from its yearly codebooks, is allowed too, with `origin: rule`; its periods are only as fine as the releases built. Each line has:
- the variable's `name` and `table`, its earlier `names` with the waves each applies to (names in another of the publisher's products, such as YRBSS's single-year files, name that product's `source`), and the publisher's `element` id when there is one;
- the publisher's `periods`, in wave units;
- its `attributes`: each row's label, verbatim, and its code in each period, or `null` where the publisher shows none.

A history can generate any wave's codes, compare releases row by row, and generate `codes_changed` and `renamed` links by rule. When the publisher prints several matrices for one variable (FARS's `HARM_EV` has one for 1975–1981 and another from 1982), join their periods into one history, without matching rows across them, and say so in its `note`. Periods record changes only where the publisher's columns change. A change inside a period, such as FARS's `WEATHER` code 99 relabeled in 2018 within the 2013–Later column, survives only in the label's own year note ("Unknown/Reported as Unknown (Since 2018)"), which stays verbatim. A rule that compares releases may read those notes: a label ending "(Since Y)" marks a change in wave Y, inside its period. FARS's link rule does this for `WEATHER`, `SEAT_POS` and `REST_USE` code 99, and the 2017 and 2024 data confirm it.

The file is optional. A dataset whose documentation covers one release at a time doesn't need it, and a variable without a history is fine. The format is provisional (§10).

## 6. Derived properties and annotations

These support search. They differ in what they let an agent claim. A publisher's own subject lists aren't annotations: they're groups of kind `subject` (§5.1).

| | Derived properties | Annotations |
|---|---|---|
| Examples | scale signature (agree/disagree 5-point, yes/no, thermometer) | topic tags, aliases ("fair housing law" for `racopen`), summaries, series |
| Made by | a named, versioned rule in the shared library | a person, a rule or a model |
| Files | `metadata/derived/<property>.jsonl`, generated | `metadata/annotations/<name>.jsonl` |
| Exact? | Yes, given the rule | No |
| Supports | `complete_by_rule` results | `approximate` results only |

Neither ever overwrites a source field.

A **series** annotation groups one variable per release into a concept readers follow over time ("depression diagnosis, 2011–2023"), across renames no link states. Its `value` is the series id. It's ours, not the publisher's, so it stays separate from links (§5.2), and results built on it are `approximate`.

## 7. Generated views

All three forms are generated by the shared library from the records above, with corrections applied, and are never edited by hand. Each generated file starts with a header naming the library version and a hash of the inputs, so `pdt check` can tell whether it is current. A JSONL file can't hold a comment, so its first line is a header object, `{"shard": {...}}`, and `agent/manifest.json` lists every generated file with its input hash.

**For people, `docs/`.** A static site with one page per variable: label, question text (each wording, with where it applies), the value set with missing types, availability as a table of waves by forms, notes, corrections with their evidence, links to other releases, and a link to the publisher's page. Also a page per group, per release, and per pair of adjacent releases saying what changed.

**For code.** The JSONL files themselves, which anything can read, and the shared library's Python API: lookup by name (case-insensitive), values, availability, missing-value recoding by type, and release comparison.

**For LLMs, `agent/`:**

- `index.md`: what the dataset is, how the shards are organized, and a table of shards with variable counts and approximate token sizes;
- shards by group, by release and by scale signature, plus annotation-based shards that are labeled as such; each shard small enough to read in full (about 20,000 tokens at most). The JSONL form of a shard may be compact: availability as runs of years by form, and one origin per record when its codes share one. The full records in `metadata/` stay canonical, and the shard's header points to them;
- each shard in two forms: JSONL, and one line per variable for reading (`name | waves | scale signature | label | question text, truncated`);
- a skill file telling an agent how to use these, and that every search result must say whether it is `complete`, `complete_by_rule` or `approximate` (below).

**What the completeness labels promise.** A label describes how a result was produced, not how confident anyone is in it. The search tools assign it; the agent doesn't choose it.

| Label | The result is | Allowed in the filter |
|---|---|---|
| `complete` | every record in scope that matches the filter, with nothing else | only fields whose origin is `publisher`, `upstream_package`, `data_file` or `hand`, and groups with those origins |
| `complete_by_rule` | the same, but the filter also uses derived properties or rule-made groups | the above, plus derived properties and `origin: rule` groups, each with its rule version |
| `approximate` | anything else: text search, annotations, or a result an agent assembled itself | anything |

When two filters return the same set, as a publisher's subject and a rule-made battery can, report the stronger label: `complete`, then `complete_by_rule`, then `approximate`.

Every result carries what's needed to rerun it: the release or releases in scope, the number of records in scope, the filter as data, and the rule versions used. A `complete` result is correct if rerunning the filter on the same records returns the same set. That can be tested, and the test suite does so. A `complete` label is only as good as the fields it filters on. "Every item on ballot A in 1985" is complete with respect to the recorded availability, which `pdt check` compares with the data (C5).

**For data-dict, `export/data-dict/<release>.yaml`.** One data-dict file per release, so data-dict's validator and renderer work on the repo. Information data-dict can't hold (missing types, links, corrections, provenance) stays in our files.

## 8. Terms and data

Before anything built from a dataset ships, `dataset.yaml` records the terms of use, reviewed by a person (`reviewed_by`, `reviewed_on`):

| Field | Question |
|---|---|
| `data` | May the data be redistributed? |
| `documentation` | May the publisher's documentation be redistributed? |
| `metadata` | May the records we build from it be published? Usually the same as `documentation` |
| `llm_processing` | May the documentation's text be sent to a hosted LLM? |

`ship` means yes, `build-only` means users must get it from the publisher themselves, and `unknown` means not yet reviewed. `unknown` blocks shipping anything that depends on it. Per-file terms in `sources.yaml` may be stricter than the dataset's, never looser.

Rules:

- Data is never committed to git. When `terms.data` is `ship`, it goes in a GitHub release with SHA-256 sums, and `download.py` can fetch the release. When it is `build-only`, `download.py` fetches it from the publisher or explains the manual steps.
- A data release holds two things: the publisher's files, unchanged, so anyone can verify them against the publisher; and the same data in the common format, written by the build, so the shared library reads every dataset the same way.
- **The common format** is one parquet file per release ([design](planning/missing_codes_design.md)):
  - There is one file per release, or one per table for a release with tables; the file metadata names the table.
  - The file holds the variables the repo has records for, not every column of the publisher's file. When the terms allow, the publisher's file ships unchanged beside it, with the rest.
  - Each variable has a **value column** with its valid answers, typed as in its record, and null wherever the answer is missing or unresolved. Codes the publisher lists as valid stay in the value column.
  - Each variable that has any codes also has a **code column**, `<name>__code`. It holds the code as text, exactly as in the record's `values` (`".d"`, `"98"`, `"."`), and is null where the answer is valid. Dimension columns such as year and ballot are variables like any other.
  - A `_row` column numbers the rows in the publisher's order. Names ending in `__code`, and `_row`, are reserved.
  - The file's metadata records the dataset, the release, the version of the standard, the SHA-256 of the publisher's file, the SHA-256 of the `variables.jsonl` used to split it, and which code texts were the publisher's own missing tokens (Stata's `.d`) rather than ordinary values (the ANES's 98), so every cell can be rebuilt exactly.
  - A value is a code only if its type matches: a number matches a numeric code in the record, a string matches a string code. The string `"98"` isn't the code 98.
  - The file is split with the **corrected** records: the source records with `corrections.jsonl` applied, as the views and the export see them. So a code an `inferred` correction resolves (ANES VCF0878's 2024 code 2) is a value in the file, not a code. The file's metadata lists the corrections applied, with their confidence, and its identity includes `corrections.jsonl`'s SHA-256 as well as `variables.jsonl`'s.
  - The build proves the conversion is lossless: it rebuilds every cell of the publisher's file from the parquet file and compares them.

  The shared library (`pdt.data`) does the splitting, writing, rebuilding and recoding; each dataset supplies only a reader for the publisher's format.
- `scripts/extract.py` reads the common format and writes the extract the user asks for, recoding missing values by type with the shared library.
- `download.py` (`pdt download`) refuses to fetch until the user passes `--accept-terms`. Without it, it prints the terms' URL and summary from `dataset.yaml`. The flag is the same for every dataset. A source converted after download (a PDF codebook to text) names its converter in `sources.yaml`'s `convert`, because the checksum depends on it.
- When `metadata` is `build-only`, the repo ships the build code and not the records; users build the records locally.
- When `llm_processing` is not `allowed`, no record may have `origin: model`.

An agent that reaches a terms question stops and asks a person.

## 9. Definition of done

`pdt check` runs these checks. A repo meets the standard when none fails. Checks marked "data" need the data files and are skipped, with a notice, when they are absent.

| ID | Check | Needs | On failure |
|---|---|---|---|
| C1 | Every file validates against its schema | | fail |
| C2 | Ids are unique: (release, name) for variables, `id` for groups, corrections and code lists. Every reference resolves: group members, link ends, correction and annotation targets, source ids, release ids, a record's `code_list`. A code is in a record's list or its `values`, not both | | fail |
| C3 | Coverage: every variable in the repo's data file has a record, and every record matches a variable in it. A slice's data file holds only the slice's variables, so the check is against the repo's file, not the publisher's | data | fail |
| C4 | Codes: every code in a `<name>__code` column appears in `values`. Valid values that `values` doesn't list are reported. The common format doesn't keep the source's value labels, so each build compares those labels with `values` before writing the file | data | fail on unlisted codes; report unlisted valid values |
| C5 | Availability: every wave in `availability` has non-missing values in the data, and every wave with non-missing values is in `availability`. Version 0.1 compares waves only, not forms or counts, and skips a table with no wave column in a release with several waves | data | warn |
| C6 | Provenance: every source used by a release has `fetched_on` and `sha256`; every upstream package has `version`. Reports counts of records without label, question text or values, of unresolved codes, and of unreviewed model output | | fail on missing hashes; report the rest |
| C7 | Each correction's `original` still appears in its target | | fail |
| C8 | `agent/` and `export/` are current with the records, and `docs/` too wherever it exists (a repo may build `docs/` for Pages without committing it, §2) | | fail |
| C9 | Terms: nothing whose terms are `build-only` or `unknown` is published, meaning pushed to a git remote or put in a data release. A repo with no remote may commit such files locally, and the check reports them instead of failing. No `origin: model` when `llm_processing` isn't `allowed` | | fail (report only when there's no remote) |
| C10 | Every extension key in the records is listed in `EXTENSIONS.md` | | fail |
| C11 | README has the sections in §2.3; CLAUDE.md exists | | fail |
| C12 | Keys and references hold in the data: each table's `key` is unique and non-blank, and each reference (§2.1) finds its target row, for the rows its `when` selects | data | fail |

`pdt check` is in the shared library, [`lib/pdt/`](lib/pdt/). Version 0.1 implements every check. C8 compares the manifest each generator writes (the SHA-256 of `dataset.yaml` and all of `metadata/`) with the current records, and only reports a different toolkit version. The data checks read `data/processed/` and skip a file, with a notice, when it's missing or when its `metadata_sha256` doesn't match the current records. To run it from a dataset repo with a toolkit checkout next to it:

```bash
PYTHONPATH=../PublicDataToolkit/lib python -m pdt check .
```

Or install the toolkit (`pip install -e ../PublicDataToolkit`) and run `pdt check`. [`schema/check_examples.py`](schema/check_examples.py) runs C1 on the examples in [`schema/examples/`](schema/examples/).

## 10. Provisional parts

The spike should try to break these:

- **One `Group` type** for sections, batteries, modules and forms. A section organizes a document, a battery is questionnaire structure, a module is about administration, and a form is about who got which questions. They may need different fields.
- **`Link` relations as a flat list.** Identity (`same_item`), change (`renamed`, `wording_changed`) and derivation (`derived_from`) are different kinds of statement. A list lets a pair carry several, but it may not be enough.
- **Availability as (wave, form, sample, mode, phase).** Tested on GSS ballots and ANES pre/post so far. MTF forms are the next test; an open-portal dataset, which has snapshots rather than waves, is the one after.
- **Missing types.** Eleven types, from the GSS, ANES, NSFG and FARS. `unknown` was added for administrative data and `unspecified` for codes marked missing without a reason. MTF may need more.
- **Provenance per field rather than per value.** Values, missing codes and question wordings have their own origin; other fields share one per field.
- **Versioned schema paths.** At 1.0, schemas move to `schema/v1/` and their `$id`s include the version, so older versions stay available to `pdt check`.
- **The common data format** (§8) was adopted after review, but no release has used it yet. MTF and NSFG will test it further.
- **Code histories** (§5.4) were added for FARS's code matrices and so far have one implementation. The ANES CDF and the GSS cumulative file may need them too; whether one format fits all three is untested.
- **Tables** (§2.1) were added for the NSFG and FARS and are tested only on toy data so far. Code-list tables (Chicago's IUCR) work for joins in the data; their codes as metadata are shared code lists (§4.5).
- **Shared code lists** (§4.5) are new, with two uses so far, Chicago's IUCR codes and the GSS occupation lists. Lists shared *across* datasets, such as FIPS state codes or Census occupation codes used by several repos, are out of scope: each dataset keeps its own list (FARS and BRFSS use different subsets of the state codes).

Record what breaks, and why, on the [project board](PROJECT_BOARD.md) under Task 5.
