# Versions, layout and names for dataset repos (Task 8)

**Status:** decided 2026-11-19 (§4). Applied to [`STANDARD.md`](../STANDARD.md) §1–2.

The goal: many dataset repos, built by different people with this toolkit, that look alike, can be found and parsed by name, and can be brought up to a newer version of the standard later.

## 1. Versioning

### 1.1 One version number

A dataset repo depends on three things that change: the standard (`STANDARD.md` and `schema/`), the template files copied into the repo, and the shared library that checks it and generates its views. Proposal: **one version number for all three,** set by tagging a release of this repo. A repo that says it meets `standard_version: "1.2"` was made from the v1.2 template and is checked with the v1.2 schemas. Separate numbers would let them get out of step, with no clear gain.

[Semantic versioning](https://semver.org/), applied to dataset repos:

| Change | Example | Version bump | What a dataset repo has to do |
|---|---|---|---|
| Breaking | a field renamed or restructured; a new required file | major (1.x → 2.0) | run a migration (§1.3) |
| Additive | a new optional field; a new check that only warns | minor (1.2 → 1.3) | nothing; update when convenient |
| Fix | documentation, a bug in a check | patch | nothing |

Until 1.0, during the spike and shortly after, anything can change and there are no migrations. Only a few repos exist then, so they can be rebuilt.

### 1.2 Use Copier, not cookiecutter, for the template

CCDS uses cookiecutter, which generates a project once and has no way to update it. [Copier](https://copier.readthedocs.io/en/stable/updating/) does:

- A generated repo has a `.copier-answers.yml` that records the template's git tag and the answers given when it was created (dataset id, publisher, and so on).
- `copier update` reads this repo's tags, takes the latest, and applies the difference between the old and new template to the dataset repo. Conflicts appear as inline markers or `.rej` files for review.
- The template can declare migrations: scripts that run when a repo crosses a given version.

### 1.3 What an update touches

A dataset repo has three kinds of files, and each updates differently:

| Files | Examples | How they're updated |
|---|---|---|
| From the template | CI workflow, `tests/`, `Makefile`, the skeletons of README, CLAUDE.md and `download.py` | `copier update` |
| Generated | `docs/` (the site), `agent/`, `export/` | regenerated by the new version of the shared library |
| Specific to the dataset | `build/` parsers, `corrections.jsonl`, hand-made inputs, `sources.yaml` | a Copier migration for mechanical changes (rename a field in every JSONL line); for the rest, an upgrade guide, `instructions/upgrade/v1-to-v2.md`, that an agent follows |

The third kind is the hard part. A Copier update can't rewrite a parser. The upgrade guide is what makes a major version workable: it lists each change, how to make it, and how to confirm it worked. The repo is upgraded when `pdt check` passes at the new version.

### 1.4 Keep old schemas

Schemas move under versioned paths (`schema/v1/variable.schema.json`), and `$id` includes the version. `pdt check` reads `standard_version` from `dataset.yaml` and validates against that version's schemas. A repo that isn't upgraded still passes against v1, so nothing breaks just because the toolkit moved on.

## 2. Cookiecutter Data Science

[CCDS v2](https://cookiecutter-data-science.drivendata.org/) (DrivenData) generates this layout: `data/{raw,interim,processed,external}`, `docs/` (MkDocs), `models/`, `notebooks/`, `references/`, `reports/figures/`, a Python module with `config.py`, `dataset.py`, `features.py`, `modeling/` and `plots.py`, plus `Makefile`, `pyproject.toml` and `README.md`. Its [opinions](https://cookiecutter-data-science.drivendata.org/opinions/): analysis is a DAG; raw data is immutable; data mostly stays out of git; notebooks for exploration, source files for repetition; build from the environment up; secrets in `.env`; adapt from a consistent default.

### 2.1 Should dataset repos follow CCDS?

**No.** CCDS is built for an analysis project, which goes from data to features to models to reports. A dataset repo is a data product: it builds metadata from documentation and publishes it in three forms. Following CCDS would give each repo three directories with no job (`models/`, `reports/`, `notebooks/`) and a module whose `features.py` and `modeling/` have none either, and it has no place for `metadata/`, `agent/` or the sources manifest.

GssExtract shows the cost. It was generated from CCDS v1, and the inventory found the `make_dataset.py` stub never filled in and Makefile targets broken by a hyphen in the project name (inventory §3.4).

A CCDS analysis project is better seen as a **consumer** of dataset repos: it downloads the data from a dataset repo into its own `data/raw/` and uses the metadata through the shared library.

### 2.2 What to adopt from CCDS

Use the same names where they mean the same thing, so the repos look familiar to CCDS users:

| From CCDS | In dataset repos |
|---|---|
| `data/raw/`, immutable, gitignored | Same. `download.py` writes here, and the checksums in `sources.yaml` guard immutability |
| `data/interim/` | Same: parser intermediates such as `pdftotext` output |
| `data/processed/` | What goes into the data release, when terms allow |
| `references/` for data dictionaries and manuals | Publisher documentation the terms allow us to commit, as MarriageNSFG's `codebooks/` does. Build-only documentation stays in `data/raw/` |
| `docs/` (MkDocs) | The generated site goes in `docs/`, so GitHub Pages can serve it without extra setup. MkDocs is a reasonable generator for it |
| `Makefile` with standard targets | The same targets in every repo: `make download`, `make build`, `make views`, `make check`. Identical commands across repos are what make them feel like one family |
| Analysis is a DAG | The Makefile encodes it: sources → records → views → check |
| Secrets in `.env` | ICPSR and other logins go in a gitignored `.env`, read by `download.py` |
| `pyproject.toml`, environment first | Same, with the shared library as a dependency |
| `config.py` with paths | Paths resolved from the file, not the working directory, which fixes the bug the inventory found in three scripts |
| Adapt from a consistent default | Weaker here: `pdt check` enforces the parts that must be the same, and everything else may vary |

What not to adopt: `models/`, `reports/`, `features.py`, `modeling/`, `requirements.txt` plus `setup.cfg` (one `pyproject.toml` is enough), and empty scaffold files. **A template file should do something on day one, or not be there.**

## 3. Names

### 3.1 Proposal

```text
pdt-<dataset-id>
```

- `pdt` is a fixed prefix for PublicDataToolkit.
- `<dataset-id>` is the `id` in `dataset.yaml`: lowercase letters, digits and hyphens, starting with the name people already use for the dataset.

| Dataset | Repo |
|---|---|
| General Social Survey, cumulative file | `pdt-gss` |
| ANES Time Series Cumulative Data File | `pdt-anes-cdf` |
| Monitoring the Future, 12th grade | `pdt-mtf-12` |
| National Survey of Family Growth | `pdt-nsfg` |
| Chicago crimes on the city portal | `pdt-chicago-crimes` |

It parses with one regular expression, `^pdt-([a-z0-9]+(?:-[a-z0-9]+)*)$`, and the dataset id is everything after the prefix.

### 3.2 Why this form

- **A prefix, not a suffix** (not `gss-pdt`). Repos sort together in a list of repos, the name says "built to the standard" up front, and parsing is trivial. A suffix reads more naturally but scatters the repos.
- **No language in the name.** gssrdoc is an R package, so its name says R. A dataset repo is meant to be language-neutral: JSONL, a static site and plain-text shards. Language support lives in the shared library (Python first, maybe R later), which reads any `pdt-` repo: something like `pdt.load("gss")`. Per-dataset packages shouldn't be necessary. If someone publishes one anyway, the derived names would be `pdt-gss` on PyPI (import `pdt_gss`) and `pdtgss` on CRAN, since R package names can't contain hyphens.
- **No version, release or publisher in the name.** A repo covers every release and outlives versions of the standard. The publisher is in `dataset.yaml`. Add a qualifier only to tell apart two products of one study (`anes-cdf` and `anes-panel`) or two jurisdictions (`chicago-crimes`).
- **Hyphens in the repo name, underscores in Python.** The template derives the module name (`pdt_gss`), so the GssExtract hyphen bug can't recur.

### 3.3 Avoiding two `pdt-gss` repos

Repos live under different owners on GitHub, so two people could both make `pdt-gss`. Two small things help:

- **A registry in this repo,** `DATASETS.md` or `registry.yaml`: dataset id, repo URL, maintainer, standard version. Claim an id with a pull request before building. The registry is also how people find the repos.
- **A GitHub topic,** `publicdatatoolkit`, on every dataset repo, so a search finds the repos that aren't registered.

### 3.4 Risks

- `pdt` is short and already used for other things, such as PHP Development Tools. It's distinctive enough next to a dataset id, and the GitHub topic disambiguates. A longer prefix such as `pdtk-` is no clearer.
- The prefix ties every repo name to this toolkit's name. If the toolkit is renamed, the repos keep the old prefix. So settle the toolkit name before the first public dataset repo.

## 4. Decisions (Allen, 2026-11-19)

1. **Versions:** one version number for the standard, the template and the library, with Copier for updates.
2. **Layout:** dataset repos don't follow CCDS, but use its names for `data/`, `references/`, `docs/`, the Makefile and `.env`.
3. **Names:** `pdt-<dataset-id>`, with no language in the name.
4. **Registry:** a registry of dataset ids in this repo, plus the `publicdatatoolkit` GitHub topic.
